## 2. Как текущий проект ложится на оконный бизнес

Текущий проект уже имеет почти все базовые блоки:

- `orders` / `order_core.tsx` - ордер как центральная сущность.
- `measurement_orders` / `MeasurementOrdersView.tsx` - отдельный поток замеров.
- `warehouse`, `procurement` - склад, поставщики, закупки, движения.
- `OrderDocumentsBuilder.tsx` - конструктор КП, договора, акта.
- `equipment` + BOM - каталог оборудования с автодобавлением комплектующих.

Для окон нужно заменить смысл `equipment`:

- Старая предметная модель удаляется из активного продукта.
- Нужно: изделие/проем/конструкция + размеры + опции + комплектующие + монтажные/отделочные работы.

Существующую идею BOM надо сохранить, но сделать ее не “по метрам трассы”, а “по геометрии и конфигурации изделия”.

## 3. Новая доменная модель

### 3.1. Заказ

`order` остается верхним уровнем:

- клиент, телефон, адрес;
- тип заказа: `windows`, `doors`, `balcony_glazing`, `balcony_finish`, `repair`;
- статус;
- замер;
- КП;
- договорные документы;
- производство/закупка;
- монтаж;
- акт и гарантия.

### 3.2. Проем / конструкция

Нужна новая сущность `opening` или `window_construct`:

- `id`
- `order_id`
- `room_name` / помещение
- `location_label` - кухня, спальня, балкон, лоджия, входная дверь
- `width_mm`
- `height_mm`
- `quantity`
- `construction_type` - окно, балконный блок, дверь, лоджия, москитная сетка, добор/откос
- `profile_system` - Brusbox 60, Brusbox 70, Rehau Blitz 60, Rehau Grazio 70, ORAS R-line и т.д.
- `glass_unit` - СП24, СП32, СП40
- `color_inside`, `color_outside`
- `lamination_category`
- `hardware_type` - Futuruss, Roto, Maco, Forwin
- `opening_scheme_json`
- `options_json` - подоконник, отлив, откосы, сетка, тонировка, доборы, ручка с ключом
- `notes`

### 3.3. Схема изделия

Для КП системе нужна визуальная схема окна/балкона с размерами. Минимальная структура:

```json
{
  "type": "window",
  "widthMm": 1400,
  "heightMm": 1300,
  "segments": [
    {
      "id": "s1",
      "x": 0,
      "y": 0,
      "w": 700,
      "h": 1300,
      "kind": "fixed",
      "opening": "none"
    },
    {
      "id": "s2",
      "x": 700,
      "y": 0,
      "w": 700,
      "h": 1300,
      "kind": "sash",
      "opening": "tilt_turn",
      "handleSide": "right"
    }
  ],
  "addons": {
    "sillDepthMm": 250,
    "mosquitoNet": true,
    "dripCap": true,
    "slopes": "pvc"
  }
}
```

Фронтенд должен рендерить эту схему как SVG/Canvas внутри КП и спецификации:

- наружные размеры: ширина и высота;
- деление на створки;
- тип открывания: глухая, поворотная, поворотно-откидная, дверь, раздвижная;
- ручка/сторона открывания;
- подписи по опциям: сетка, отлив, подоконник, добор, ламинация.

## 5. Расчет КП

Нужен отдельный расчетный движок `window_pricing`.

Вход:

- список конструкций/проемов;
- размеры;
- профильная система;
- стеклопакет;
- фурнитура;
- цвет/ламинация;
- дополнительные профили;
- подоконники/отливы/откосы/сетки;
- демонтаж/монтаж/подъем/доставка;
- скидка/НДС/предоплата.

Выход:

- строки КП;
- себестоимость;
- продажная цена;
- потребность в закупке/производстве;
- схема изделия для печати;
- данные для договора и спецификации.

Правила:

- базовая цена изделия берется из матрицы `profile + glass_unit + width + height`;
- если размер не попал точно в матрицу, нужен режим округления: вверх до ближайшей ширины/высоты или запрет с ручным подтверждением;
- фурнитура добавляется по типу створок/дверей;
- ламинация считается процентом от базовой цены по категории и стороне;
- тонировка/сетка/доборы/подоконники/отливы считаются отдельными строками;
- монтаж и отделка считаются по `work_rates`: шт, м.п., м2, услуга.

## 6. Документы

Документы должны генерироваться из оконной спецификации и схем изделий:

- КП для окон/балконов:
  - титул;
  - данные клиента и объекта;
  - таблица конструкций;
  - схема каждой конструкции;
  - комплектация;
  - итоговая сумма, предоплата, остаток;
  - сроки, гарантия, условия.
- Договор на монтаж оконных и дверных конструкций:
  - взять структуру из загруженного договора;
  - оставить юридические условия как шаблон;
  - заполнители: номер, дата, клиент, адрес, сумма, предоплата, срок изготовления/монтажа.
- Договор на отделку балкона:
  - отдельный тип документа.
- Спецификация:
  - обязателен список работ/материалов;
  - обязательно место для подтверждения точности замеров;
  - схемы окон/балконов.
- Акт:
  - список выполненных работ;
  - фраза о приемке без претензий;
  - подписи.
- График платежей:
  - несколько строк дат/сумм/подписей.

Важно: для `.docx` лучше не оставаться на HTML `.doc`. Нужен нормальный DOCX/PDF-рендерер, потому что в оконном бизнесе документы будут подписывать и хранить.

## 8. Что лучше не делать в первом шаге

- Наследованные отраслевые модули удаляются или выводятся из активного маршрута, рабочие механики переносятся в оконную модель.
- Не пытаться хранить прайс окон как обычные складские позиции: матрицы размеров потеряются.
- Не делать схему окна только картинкой: нужна структурная JSON-модель, иначе нельзя пересчитывать и редактировать.
- Не смешивать “складские материалы” и “прайсовые изделия поставщика”: окно под заказ, фурнитура/доборы/расходники могут быть складом.

## 10. Главный архитектурный вывод

Проект можно развернуть под оконный бизнес без полной переделки. Ядро остается:

`лид -> ордер -> замер -> КП -> договор/спецификация -> закупка/производство -> монтаж -> акт`.

Ключевая новая часть - `window_construct + opening_scheme_json + pricing_matrix`. Именно она отличает оконный бизнес от старой предметной модели и должна стать центральной доменной моделью.
